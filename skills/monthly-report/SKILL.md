# 月度绩效生成

按**用户自己的模板**，把某段时间内的 git 提交整理成月度绩效；或根据用户口述的功能描述，写出下月绩效计划。

三条底线，贯穿全程：

1. **只写有依据的内容。** 提交记录、用户口述、历史文件之外的东西一律不写。不编造指标（百分比、耗时、用户数）、不扩大范围（提交只做了一半就不写成「全部完成」）。
2. **总分不动。** 模板里的总分和用户确认的分值拆分是硬约束，各小项分值之和必须等于它。
3. **该问就问。** 模板有没有换、其他任务占多少分、哪些邮箱是本人、未推送的提交算不算——这些不要自己猜。

## 0. 数据目录

用户的模板和历史输出放在**插件自己的持久数据目录**，不在本技能里自带，首次使用时由你创建：

- 数据目录：`${CLAUDE_PLUGIN_DATA}`。如果这个变量没有被替换成真实路径（原样显示为 `${CLAUDE_PLUGIN_DATA}`），改用 `~/.claude/monthly-report/`。
- `template.md`：用户的绩效模板（原样保存）。
- `history/<项目名>/<YYYY-MM>.md`：每月定稿；规划稿存为 `<YYYY-MM>.plan.md`。项目名取当前 git 仓库根目录名。

开始前先用 Bash 解析出数据目录的**绝对路径**并确认存在（不存在就创建），后面都用这个路径。

## 1. 模板

- **`template.md` 不存在**：请用户贴出绩效模板（也可以贴上个月写好的成稿，从中提取）。原样存入 `template.md`。用户没有模板时，读本技能目录下的 `references/template-example.md` 给他看一份样例，让他按需改。
- **`template.md` 存在**：列出模板里的大项标题和分值（只列标题，不要整篇复述），问一句：「沿用这份模板，还是换了？」换了就让用户贴新的，覆盖前先把旧的另存为 `template.prev.md`。

从模板中识别并向用户确认三件事：**总分**、**条目层级**（大项 / 小项 / a b c 子点）、**是否带「成果描述」**。识别不出来就问，不要硬猜。

## 2. 确定模式

- **总结**（默认）：写已经做完的月份。需要时间范围。
- **规划**：写下个月要做的。需要用户给出功能清单。

用户没说清楚就问一次。

## 3. 分值拆分

问：「这个月除了当前项目，还有别的任务吗？各占多少分？」

- 没有：当前项目占满总分。
- 有：当前项目 = 总分 − 其他任务分值。其他任务**不读代码**，由用户口述一两句话，你只负责按模板格式排版，并说明「这部分内容来自你的口述」。用户没给细节就只展开到他给的程度，不补充。

## 4. 总结模式

### 4.1 收集提交

先确认时间范围，用**带时分秒**的边界（只写日期时 git 会用当前时刻补全，容易漏掉最后一天）：

- 某个月：`--since="2026-10-01 00:00:00" --until="2026-10-31 23:59:59"`
- 某个提交之后：`<hash>..HEAD`

**先确认哪些作者是用户本人**，不要只信 `git config user.email`（同一个人可能用过多个邮箱）：

```
git shortlog -sne --no-merges --since="…" --until="…" HEAD
```

末尾的 `HEAD` 不能省：在非交互环境里不带它，`shortlog` 会去读标准输入，什么都不输出。

把结果给用户看，让他勾选自己的名字 / 邮箱。然后取提交（`-E` 让 `--author` 支持 `a|b` 多个）：

```
git log -E --author="邮箱1|邮箱2" --no-merges --since="…" --until="…" --date=short --format="%h|%ad|%s%n%b%n-----"
```

注意：

- 正文很长的提交（如 squash 合并）先看正文；信息不够再 `git show --stat <hash>` 或读相关的设计文档，**不要通读代码**。
- **未推送的提交**：有上游分支时用 `git log @{u}..HEAD --oneline` 看有哪些；问用户这个月要不要算进去，由他决定。
- 当前目录不是 git 仓库，或工作涉及多个仓库：问用户还有哪些仓库路径，逐个用 `git -C <路径>` 收集。
- 用户明确说这个月没有代码类工作：跳过本节，只排版口述内容。

### 4.2 归并成功能点

- **按功能主题归并，不按提交类型**。「新增接口」「修复 bug」「补测试」「更新文档」属于同一个功能时合进同一条，不要各列一条。
- 一个大项下面 3～6 个小项；小项一句话说清「做了什么」，用「完成 / 支持 / 新增 / 优化 / 修复」开头，不写提交哈希、不写文件名。
- 纯文档、格式化、依赖升级、重命名这类提交，除非它本身就是这个月的主要工作，否则不单列。
- 同一功能被反复改（做了又撤）的，只写最终结果。
- 一个提交横跨几个功能时，拆开归到各自的条目里。
- 能精简的精简、能合并的合并——每个小项要有信息量，别凑数。

### 4.3 给分

按工作量（提交数量、涉及面、复杂度）给每个大项一个**建议分值**，各项之和等于当前项目分值，并用一句话说明依据。分值由用户最终拍板，你只给建议。

### 4.4 对照历史，找重叠

读 `history/<项目名>/` 下最近 1～2 个月的文件，找出：

- **重复**：这个月的某条和上个月基本是同一件事 → 提示用户，建议改成「在原有基础上新增……」的增量写法，或删掉。
- **取代**：这个月的提交把上个月的功能替换了、撤销了 → 明确写成「调整」，不要当成全新的能力来写，也不要悄悄省掉；和用户确认措辞。
- **关联**：主题相近但内容不同（例如上月做设置、本月做展示）→ 换角度写，避免读起来像重复。

历史目录为空（第一次使用）就跳过本步。

### 4.5 对照规划

如果存在同月份的 `<YYYY-MM>.plan.md`，把计划和实际对一遍：

- 计划里有、提交里找不到的 → 列出来问用户：没做 / 延期 / 在别的仓库做的。
- 提交里有、计划里没有的 → 作为「计划外」补进去。

## 5. 规划模式

让用户用一两句话描述每个要做的功能（不需要写成最终措辞）。按同样的模板排版，注意：

- 用「推进 / 计划完成 / 预计完成」，**不要**写成「完成」——还没做。
- 分值拆分、条目归并规则同总结模式。
- 用户没说清的细节，在输出里标 `（待补充）`，不要自己填。
- 保存为 `<YYYY-MM>.plan.md`（YYYY-MM 是计划要执行的那个月），月底做总结时会被 4.5 用到。

## 6. 输出与保存

1. 严格按 `template.md` 的格式输出（大项标题、分值写法、a b c 子点、成果描述的位置和长度），不要自创格式，也不要加模板里没有的栏目。带「成果描述」的模板，每个大项末尾补 1～2 句，概括做成了什么，不重复小项。
2. 输出后问：「要调整哪里？」按反馈改，改到用户满意为止。
3. 用户确认定稿后，才存入 `history/<项目名>/<YYYY-MM>.md`。文件开头写一小段元数据（时间范围、仓库、总分、当前项目分值、生成日期），其后是定稿原文。同名文件已存在时先问是否覆盖。
4. 告诉用户保存到了哪里。

## 不要做的事

- 不要把提交哈希、内部文件路径、分支名写进绩效。
- 不要读 `.env`、密钥、凭据类文件；提交里出现的密钥或内部地址不要抄进输出。
- 不要在用户没确认前保存定稿，也不要覆盖他的模板。
- 不要为了凑分值把一个小功能写成大项，也不要把一个大项拆成很多小项显得工作量大。
